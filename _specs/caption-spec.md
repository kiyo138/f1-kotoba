# 図版キャプション追加 仕様書

対象: `build.py`（本文中図版のキャプション）／ 版: 初版 ／ 起案: ディレクター

---

## 1. 目的

本文中の図版（hero を除く6枚）には現在、下に固定の案内文
「画像をタップすると大きく表示できます」が1行あるだけである。
スマートフォン（幅390px）では図中の文字が読めず、**図が何を言っているのかが読者に伝わらない**。

そこで各図の下に、**その図の主張を一文で述べたキャプション**を添える。
図中の文字が読めない読者にとって、これが図の代替となる。

副次的な目的として、第1回 `parts` の alt が実画像と一致していない欠陥を是正する（§7）。

制約として、**原稿テキスト（`f1-NN-本文.txt`）は一切変更しない**。
キャプションは画像の差し込み位置（アンカー）や alt と同じく `build.py` の `COLUMNS` が持つ。
また、**毎週の運用手順を増やさない**。新しい回の公開は今後も「`COLUMNS` に1エントリ追記するだけ」である。

---

## 2. 入力と出力

### 入力
- `build.py` 内の `COLUMNS`（唯一の手入力データ）。画像エントリのタプルに **4要素目「キャプション」を追加できるようにする**。
  - 形式: `("サフィックス", アンカー, "alt", "キャプション")`
  - **4要素目は省略可能**。既存の3要素タプルはそのまま動くこと（後方互換）。
- 原稿テキスト `f1-NN-本文.txt`（**読み取りのみ。変更禁止**）
- 図版 PNG（変更なし）

### 出力
- `docs/NN/index.html` の `<figure class="fig">` 内 `<figcaption>` に、キャプション文が出力される。
- キャプション未指定の回・画像では、**現状どおり案内文のみ**が出力される（§5 フォールバック）。
- hero 画像にはキャプションを出さない（装飾のため）。hero に `<figcaption>` を新設もしない。

### 3.2 各文の根拠（何を言語化したか／本文と重ならない理由）

1. **f1-01-diagram.png**
   - 図の何を言語化したか: 同一のカーブに青の実線（思い通りのライン）と赤の破線（アンダーステア）を**重ねて並置している構図そのもの**。すなわち「2本を重ねて比べる」という比較関係。
   - 本文と重ならない点: 本文は1台の挙動として「そのまま外へ流れていく」と述べるのみで、**2本の線を重ねて比較しているという図の構造には触れていない**。

2. **f1-01-parts.png**
   - 図の何を言語化したか: マシンを**真横から見た図**に7つの部位名（ノーズ／ハロー／エアボックス／リアウイング／フロントウイング／タイヤ／サイドポッド）が引き出し線で置かれている、という位置関係。
   - 本文と重ならない点: 本文にノーズ・ハロー・エアボックス・サイドポッドという語は一度も出てこない。図だけが持つ情報である。

3. **f1-02-tyres.png**
   - 図の何を言語化したか: 左からスリック→インターミディエイト→フルウェットと並び、**左から右へ溝が深くなるほど排水量が増える**という順序・段階関係。
   - 本文と重ならない点: 本文は3種類を箇条書きで列挙し、30L／85L を個別に述べるだけで、**「左から右へ深くなるほど増える」という並びの意味は述べていない**。数値は使わないため図中数値との齟齬も生じない。

4. **f1-02-range.png**
   - 図の何を言語化したか: 乾いた路面から大雨までを**1本の帯**にしたとき、**真ん中の最も広い区画をインターが占める**という範囲・幅の関係。
   - 本文と重ならない点: 本文は「中途半端な状況で履くタイヤ」と性質を述べるが、**帯の中で占める幅が最も広いという図固有の表現はしていない**。112% の数値には触れないため図中表記と衝突しない。

5. **f1-03-wing.png**
   - 図の何を言語化したか: 左に飛行機の翼、右にF1のウイングを**左右に並べ**、同じ形に対して**矢印が上向きと下向きで正反対を向く**という対比関係。
   - 本文と重ならない点: 本文の「さかさまに取り付けたもの」「飛ぶための翼ではなく、飛ばないための翼」という言い回しを避け、**左右並置と力の向きの対比**という図の構造だけを述べている。

6. **f1-03-mode.png**
   - 図の何を言語化したか: コーナー（閉）→直線（開）→コーナー（閉）と**左から順に3コマ並び、最初の状態に戻る**という時間的な順序・繰り返し関係。
   - 本文と重ならない点: 本文は各モードの働き（押しつけ最大／抵抗を減らす）と2026年の制度変更を述べるが、**「閉→開→また閉じる」と元に戻る繰り返しの並びであることは述べていない**。

## 5. 処理の流れ（build.py の変更箇所）

行番号は現状ファイルの目安。

### 5.1 `COLUMNS` の型と内容（29〜93行目）

- 29〜42行目のコメントブロックに、4要素目の説明を足す。
  ```
  ("画像サフィックス", アンカー or None, "altテキスト" or None, "キャプション")  # 4要素目は省略可
  ```
- 44行目の型注釈を、3要素・4要素のどちらも許す形に緩める。
  例: `dict[str, tuple[str, list[tuple]]]`（過度に凝った型は不要）。
- 各画像エントリに §3.1 のキャプションを4要素目として追加する。hero は3要素のまま（`("hero", None, None)`）。
- **第1回 `parts` の alt を §7 の文言に差し替える。**

### 5.2 画像エントリの正規化（`process_round` 冒頭 / 311行目〜）

`process_round` の引数 `images` を受け取った直後に、**4要素へ正規化した内部リストを1回だけ作る**。

- 3要素なら4要素目を `None` として補う。
- 以降 `process_round` 内は正規化済みリストのみを使う。
- 影響する既存の3要素アンパック箇所（すべて4要素対応に直す）:
  - 347行目 `declared_names = {... for suf, _, _ in images}`
  - 358行目 `for suf, anchor, alt in images:`（検証ループ）
  - 374行目 `for suf, _, _ in images:`（PNGサイズ読み取り）
  - 393行目 `for suf, anchor, alt in images:`（画像ノード生成）
- 312行目の型注釈も合わせて更新する。
- 430行目 `data["images"]` には**正規化後の4要素リスト**を入れる。これに伴い
  **1202行目 `for suf, _, _ in data["images"]:` を4要素に対応させる**（`for suf, *_rest in ...` 等）。
  ここを直し忘れると `write_site` で `ValueError: too many values to unpack` が出る。

### 5.3 キャプションの検証（358〜370行目の検証ループ内に追加）

**警告のみ。エラーで停止させない**（`warnings` に積む。`errors` には積まない）。

- hero 以外で、キャプションが `None` または空白のみ → **何も警告しない**（未記入は正常な状態。§6 参照）。
- キャプションが41字以上 → 警告
  `第NN回: f1-NN-xxx.png のキャプションが{n}字あります（40字以内を推奨）`
- キャプション中の `。` が2つ以上、または `。` が末尾以外に含まれる → 警告
  `第NN回: f1-NN-xxx.png のキャプションが二文になっています（一文にしてください）`
- hero エントリに空でないキャプションが書かれている → 警告し、**出力では無視する**
  `第NN回: hero にキャプションは出力されません（無視します）`

警告は既存の仕組みどおり `main()`（1247〜1248行目）で `警告: ...` として標準エラーに出るだけで、
終了コードは 0 のままとする。

### 5.4 img ノードへの受け渡し（393〜399行目）

- `insertions.setdefault(pos, []).append(("img", suf, alt))` を
  **`("img", suf, alt, caption)` の4要素ノード**に変える。
- 218行目の `Node` の説明コメントを `("img", suffix, alt, caption)` に更新する。

### 5.5 HTML 出力（`render_flow_node` 886〜908行目）

- 895〜907行目の `if kind == "img":` を4要素アンパックに変える。
- `<figure>` `<a class="plate">` `<img>` の出力は現状のまま（変更なし）。
- `<figcaption>` の中身だけを次の規則で組み立てる。
  - キャプションあり: キャプション + 案内文
  - キャプションなし（`None` / 空白のみ）: **現状とまったく同じ出力**（案内文のみ）
- キャプション文は他の可変文字列と同様 `esc()` を通す。HTML タグの埋め込みは許さない。

#### figcaption の DOM 構造（候補・意匠部署の裁定に従う）

**この節の最終形は architect の意匠仕様に従うこと。** 以下は候補である。

- 案A（`span` で明示的に2段）
  ```html
  <figcaption><span class="cap-text">キャプション</span><span class="cap-hint">画像をタップすると大きく表示できます</span></figcaption>
  ```
- 案B（キャプションは裸のテキストノード、案内文だけ span）
  ```html
  <figcaption>キャプション<span class="cap-hint">画像をタップすると大きく表示できます</span></figcaption>
  ```
- 案C（キャプションがあるときは案内文を出さない／統合する）
  ```html
  <figcaption><span class="cap-text">キャプション</span></figcaption>
  ```

現行 CSS（669〜675行目 `.cap-hint`）は `display:block` + `margin-top:4px` + `⤢ ` の擬似要素を持つため、
**案A・案Bはいずれも CSS 追加なしで「キャプション → 改行 → 案内文」の2段組みになる**。
案Aを採る場合、`.cap-text` に対する装飾（色・字送り）が要るかは意匠側の判断。
案Cを採る場合は「拡大できること」の告知が消える点を意匠側で了解すること。

### 5.6 hero 画像

`render_article` 内の hero 出力は**一切変更しない**。hero に `<figcaption>` を付けない。

## 6. フォールバック（キャプション未記入時）の挙動

**必須要件。エラーにしてはならない。**

| 状態 | 挙動 |
|---|---|
| エントリが3要素（4要素目なし） | キャプションなしとして扱う。案内文のみを出力。ビルドは成功 |
| 4要素目が `None` | 同上 |
| 4要素目が空文字・空白のみ | 同上（`strip()` して空なら「なし」と判定する） |
| 4要素目が41字以上／二文 | 警告を出したうえで**そのまま出力する**。ビルドは成功（exit 0） |
| hero に4要素目がある | 警告を出し、出力では無視する。ビルドは成功 |

すなわち第4回以降で書き手がキャプションを書き忘れても、
**その回は現状どおり案内文だけで公開される**。毎週の運用手順は増えない。

## 9. 想定される失敗時の挙動

| 事象 | 期待する挙動 |
|---|---|
| キャプション未記入（3要素／`None`／空白） | エラーにしない。案内文のみ出力し exit 0（§6） |
| キャプションが40字超・二文 | 警告を標準エラーに出し、そのまま出力。exit 0 |
| hero にキャプション記入 | 警告を出し無視。exit 0 |
| キャプションに `<` `&` 等が含まれる | `esc()` でエスケープして出力。HTML が壊れないこと |
| 4要素目の型が文字列でない（記述ミス） | 既存の致命的エラー方式に合わせ、`第NN回:` 付きのメッセージを `errors` に積み、**docs/ を一切書き換えず exit 1** |
| タプルが5要素以上 | 同上（`第NN回: COLUMNS のエントリの要素数が不正です`）。exit 1 |
| `write_site` の `data["images"]` アンパック漏れ | これは実装漏れであり、放置してはならない（§5.2 の注意） |

既存方針どおり、**致命的エラーが1つでもあれば `docs/` は一切書き換えない**（1241〜1245行目）。

## 10. やらないこと（過剰設計の禁止）

- キャプションを原稿テキストや外部 YAML/JSON から読む仕組みは作らない。
- 図ごとに複数キャプション、多言語、長短切り替えなどの機構は作らない。
- キャプション有無を切り替える設定フラグは設けない（未記入がそのまま「無し」である）。
- 既存の `CAP_HINT_TEXT` は固定文言のまま。設定化しない。
