# build.py 仕様書 — F1コラム静的サイト生成

対象: `C:\Users\ukyoa\Documents\claude-code\F1 Column\build.py`（新規）
版: 初版 / 2026-09-08

## 1. 目的

連載コラム「F1のことば、あいうえお」を GitHub Pages で公開する。

毎週1回分の原稿（`f1-NN-本文.txt`）と画像（PNG）が新しいフォルダに追加される。
`python build.py` を **1回走らせるだけ** で、記事ページ・索引・画像配置がすべて更新され、
`docs/` をコミットすれば公開できる状態にする。手作業の工程を一切残さない。

原稿テキストはチャットルーム投稿用の原文であり、**サイト生成のために原文を書き換えない**。
サイト固有の情報（画像の差し込み位置など）は build.py 側の対応表が持つ。

## 3. 入力

### 3.1 入力ファイル

各回のフォルダ（フォルダ名は日本語の語名。命名規則は無い）に以下が置かれている。

```
アンダーステア/  f1-01-本文.txt  f1-01-hero.png  f1-01-diagram.png  f1-01-parts.png
インターミディエイト/  f1-02-本文.txt  f1-02-hero.png  f1-02-tyres.png  f1-02-range.png
ウイング/  f1-03-本文.txt  f1-03-hero.png  f1-03-wing.png  f1-03-mode.png
```

### 3.2 読んではならないもの（重要）

| 対象 | 扱い |
|---|---|
| `インターミディエイト/f1-01-本文.txt` | 第1回の重複コピー。**読まない・触らない・削除しない** |
| `*.bak` `*.bak2` `*.bak3` `*.bak4` | 退避ファイル。読まない（例: `ウイング/f1-03-本文.txt.bak4`） |
| `_assets/` | SVG原本。サイトに含めない |
| `f1-column.md` | スキル定義。サイトに含めない |
| `シンガポールGPしおり/` | 本サイトと無関係。**一切参照しない** |

### 3.3 フォルダの自動探索を行わない

ルートを Glob して回を集める方式は採らない。理由:

- `インターミディエイト/` に第1回の重複コピーがあり、`NN=01` が2箇所から取れて非決定的になる。
  自動探索＋重複検出エラー方式にすると、解消のためにファイル削除が必要になり、裁可が要る。
- フォルダ名に規則が無い（スキル定義は `f1-column-NN/` だが実体は日本語名）。将来の名前も予測できない。

代わりに **§4 の対応表が読み取り対象フォルダを明示的に宣言する**。
表に無いフォルダは存在しないものとして扱う。これにより重複コピーもしおりも自動的に対象外になる。

回番号 NN は、宣言されたフォルダ内のファイル名 `f1-NN-本文.txt` から取る（表のキーと突き合わせて検証する。§8-2）。

## 4. 回・画像対応表（COLUMNS）

build.py 内に置く唯一の手入力データ。**週に1エントリ追記するだけ**で新しい回が公開される。

### 4.1 構造

```
COLUMNS = {
    "NN": (
        "フォルダ名",
        [
            ("画像サフィックス", アンカー, "alt テキスト", "キャプション"),
            ...
        ],
    ),
}
```

- キー `"NN"`: 2桁ゼロ埋め文字列。`"01"` `"02"` …
- 画像ファイル名は `f"f1-{NN}-{サフィックス}.png"` で組み立てる（表に書くのはサフィックスのみ）
- **アンカー**: 差し込み位置の指定
  - `None` … 冒頭（h1 直後、リード段落より前）
  - `"見出し文字列"` … その `■` 見出しの節が終わった直後（次の `<h2>` の直前、または記事末尾）
- alt: その画像の内容に即した説明文。**サフィックスが `hero` の場合のみ `None` を許し**、
  `第3回「う」ウイング のアイキャッチ画像` を自動生成する。`hero` 以外で `None` または空文字は失敗（§8-7）。
- **キャプション（4要素目）**: `<figure>` の `<figcaption>` に出す一文。**省略可**（3要素タプルはそのまま動く）。
  - 省略・`None`・空白のみなら「キャプションなし」として扱い、案内文のみを出力する。
  - hero にキャプションを記入しても、出力では無視される（警告を出す）。

### 4.2 キーの持ち方の決定と理由

**見出し文字列をアンカーに使う**（節の序数は使わない）。

- 表を読んだだけで「どの節の後か」が分かり、原稿を開き直さずに保守できる。
- 序数キーは、あとから節を1つ挿入すると全画像が黙ってずれる。文字列キーなら不一致が即エラーになる（§8-4）。
- 見出しの表記ゆれ（全角スペース等）に弱いが、それは§8-4の検証で必ず露見するので黙って壊れない。

比較は**完全一致**（`■ ` を除去し、行頭行末の空白を除いた文字列どうし）。部分一致・正規化はしない。

## 5. 本文txt → 中間表現への変換規則

1ファイルを行のリストとして読み、順に処理する。BOM があれば除去する。行末の空白を除去する。

### 5.1 ヘッダ（回数・かな・語の抽出）

ファイル先頭は `━`（U+2501, HEAVY）のみからなる罫線行で囲まれた3行。

```
━━━━━━━━━━━━━━━━━━━
【F1のことば、あいうえお】
第3回「う」　ウイング
━━━━━━━━━━━━━━━━━━━
```

- 1行目が `━` のみの行であること。次に現れる `━` のみの行までをヘッダブロックとする。
- ブロック内の `第N回「か」　語` の行から **N / かな / 語** を抽出する。
  区切りは **全角スペース U+3000**。かな は `「` `」` に挟まれた1文字。
- 抽出した N は表のキー（ゼロ埋め前）と一致すること（§8-3）。
- **ヘッダの4行は本文として出力しない。** `【F1のことば、あいうえお】` の行も捨てる。
- 抽出値の用途: `<title>` / `<h1>` / og:title / hero の自動 alt / 索引の見出し。

### 5.2 見出し

`■ ` で始まる行 → 節の開始。先頭の `■` と続く空白を除去した残りを見出し文字列とし、`<h2>` として出力する。

### 5.3 箇条書き

`・` で始まる**連続した行**を1つのリストにまとめる。`・` を除去した残りが各 `<li>`。
`・` で始まらない行（空行を含む）が現れた時点でリストを閉じる。

- 箇条書きの行は**段落連結（§5.5）の対象外**。1行＝1項目としてそのまま扱う。
- 実例: 第1回に4項目、第2回に3項目（`・スリック … 溝なし。乾いた路面用` 等）。第3回には無い。

### 5.4 段落の区切り

空行で段落を区切る。空行が2行以上連続しても段落は1つしか増えない（空段落を作らない）。

### 5.5 段落内の改行を詰める（最重要）

原文はチャット投稿用に35字前後で手折りされている。スマホでそのまま `<br>` すると二重折り返しになる。

**同一段落に属する複数行は、区切り文字を一切入れずに単純連結する。**

- 日本語なので**空白を挿入しない**。
  例: `曲がらず、` + `外へ流れる` → `曲がらず、外へ流れる`
- `<br>` は一切出力しない。
- 連結後の1段落＝1つの `<p>`。

### 5.6 リード段落（第1節より前の本文）

第1回のみ、ヘッダ直後・最初の `■` 見出しより前に段落がある（3行1段落）。
これを**リード**として `<h1>` と hero 画像のあとに `<p>` で出力する。第2回・第3回には無い（無くてもよい）。

### 5.7 フッタ（次回予告）

`─`（U+2500, LIGHT。`━` とは別文字）**のみからなる行**が現れたら、そこから先はフッタ。

- 開始罫線行より後の、罫線以外の行を「次回予告」の行として集める。
- **閉じ罫線があってもなくてもよい。行数が1行でも2行でもよい。**
  - 第1回: 開始罫線 / `次回は「い」。` / `雨のレースで…あの言葉を予定しています。` / 閉じ罫線
  - 第2回: 開始罫線 / `次回は「う」。` でファイル終端（**閉じ罫線なし・1行のみ**）
  - 第3回: 第1回と同型
- **罫線行そのものは出力しない。**
- 集めた行は§5.5と同様に**区切り文字を入れず単純連結**し、1つの流れる文として `<div class="col next-up">` 内に配置する（行ごとに `<p>` で包まない）。
- フッタ開始罫線が1つも無い場合 → 警告を出し、次回予告なしでページを生成する（致命ではない）。

### 5.8 出力しないもの

ヘッダ罫線、`【F1のことば、あいうえお】` の行、フッタ罫線、空行そのもの。

### 6.2 記事ページの構造

```
<!doctype html>
<html lang="ja">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width,initial-scale=1">
  <title>第3回「う」ウイング ｜ F1のことば、あいうえお</title>
  <meta name="description" content="（§7の抜粋）">
  <link rel="canonical" href="https://kiyo138.github.io/f1-column/03/">
  （§7 の OGP メタ）
  <style>（§6.4 のCSSを直書き）</style>
</head>
<body>
  <header class="site"><a href="../">F1のことば、あいうえお</a></header>
  <article>
    <h1>第3回「う」ウイング</h1>
    <figure><img src="f1-03-hero.png" alt="…" width="1600" height="900"></figure>
    （リード段落があればここに <p>）
    <h2>飛行機の翼を、さかさまにする</h2>
    <p>…</p>
    <figure><img src="f1-03-wing.png" alt="…" width="1600" height="780"></figure>
    <h2>…</h2> …
    <ul><li>…</li></ul>
    …
    <footer class="next"><p>次回は「え」。</p><p>ためた電気を、…</p></footer>
  </article>
  <nav class="pager">
    <a href="../02/">← 第2回「い」インターミディエイト</a>
    <a href="../">索引</a>
    （次の回があれば <a href="../04/">…</a>）
  </nav>
</body>
</html>
```

- `<h1>` は `第3回「う」ウイング`（回数・かな・語を連結。かなは鉤括弧付き）。
- 前後リンクは COLUMNS のキーを昇順に並べて自動生成する。端では該当リンクを出さない。
- **本文中の図版（hero 以外）には `<figcaption>` を付ける。** キャプションが記入されていれば
  キャプション文と案内文を出し、未記入なら案内文のみを出す。hero には `<figcaption>` を付けない。
- **JavaScript は書かない。**

### 6.3 画像の width / height

PNG の実寸を `<img>` に書き、スマホでの読み込み時のレイアウトずれを防ぐ。

PIL は使わず、**PNGヘッダを直接読む**（標準ライブラリのみ）。

- 先頭8バイトが PNG シグネチャ `\x89PNG\r\n\x1a\n` であることを確認する。
- 16〜23バイト目（IHDR の width/height）をビッグエンディアン符号なし32bit×2として読む。
- CSS 側で `width:100%; height:auto;` を当てるため、属性値は縦横比の宣言としてのみ機能する。

### 6.4 CSS

**各HTMLの `<style>` に同一文字列を直書きする。外部CSSファイル・外部フォント・CDNを一切読み込まない。**

方針（実装の裁量に委ねる細部は問わないが、以下は満たすこと）:

- フォントは端末内蔵のみ: `system-ui, -apple-system, "Hiragino Kaku Gothic ProN", "Yu Gothic", Meiryo, sans-serif`
- 本文カラム幅は最大 40rem 程度、中央寄せ。左右に余白（スマホで 1rem 以上）
- `line-height: 1.9` 前後。段落間に余白を取る
- `img { width:100%; height:auto; display:block; }`。`figure` の左右マージンを 0 にする
- 配色は画像に合わせる: 背景 `#F6F5F2` / 本文 `#191B1F` / 補助 `#5A5D64` / 強調 `#D4342A`
- `<h2>` は強調色の下線か左罫で節を明示する
- `footer.next` は補助色・小さめの字で控えめに
- `prefers-color-scheme: dark` への対応は**しない**（画像が明背景固定のため、ちぐはぐになる）

### 6.5 索引 `docs/index.html`

- 見出し `F1のことば、あいうえお` とリード1文（固定文字列）。
- **第1回から昇順**に各回を1件ずつ列挙する。各件は次を含む:
  - `01/f1-01-hero.png` のサムネイル（alt は hero の alt と同じ）
  - `第1回「あ」アンダーステア`
  - §7 の抜粋文（記事の og:description と同じ文字列）
  - リンク先は `01/`（相対）
- OGP は §7.3。

### 6.6 `.nojekyll`

`docs/.nojekyll` を 0バイトで作成する。GitHub Pages の Jekyll 処理を無効化するため（`_` 始まりのパスや将来の資材が落ちるのを防ぐ）。

### 7.1 生成規則（記事ページ）

### 7.2 og:description の生成規則（確定）

1. **取得元**: 整形後の本文の**最初の段落**（`<p>` になるもの）。
   - 第1回はリード段落、第2回・第3回は第1節の最初の段落が該当する。
   - 見出し・箇条書き・次回予告は取得元にしない。
2. 段落内改行は §5.5 で既に除去済み。残っている制御文字・タブがあれば半角スペース1個に置換し、前後を strim する。
3. **記号の扱い**: 「」（）… ※ 等はそのまま残す（読み手に意味があるため）。除去も置換もしない。
4. **長さ**: 最大 100 文字。101文字以上なら**先頭100文字で単純に切り、末尾に `…`（U+2026）を付ける**。
   句読点位置への丸め込みはしない（規則を単純に保つ）。
   - 実測: 第1回 約74字 / 第2回 約49字 / 第3回 約40字 → 現状3回とも切り詰めは発生しない。
5. 最後に HTML 属性値としてエスケープする（§9）。

### 7.3 索引の OGP

| プロパティ | 値 |
|---|---|
| `og:title` | `F1のことば、あいうえお` |
| `og:description` | `F1中継で聞こえてくる言葉を、五十音順にひとつずつ。最新は第3回「う」ウイング。`（**最新回から自動生成**） |

## 8. 検証と失敗時の挙動

### 8.1 二段階実行（部分出力を作らない）

1. **第1段階: 全回を読み込み・解析・検証する。ファイルを1バイトも書かない。**
2. 致命エラーが1件でもあれば、**検出したエラーを全件まとめて標準エラーに列挙し、終了コード 1 で終了する。** `docs/` は変更されない。
3. エラーが無ければ第2段階として書き出す。

エラーを1件目で止めずに全件出すのは、週次作業で往復を減らすため。

### 8.2〜8.9 致命エラー一覧（すべて exit 1）

| # | 条件 | メッセージに含める情報 |
|---|---|---|
| 1 | COLUMNS が宣言するフォルダが存在しない | 回番号・フォルダ名 |

## 9. HTMLエスケープ

- 本文・見出し・箇条書き・alt・title・meta の**すべての可変文字列**に `html.escape(s, quote=True)` を適用する。
- 属性値は必ず `quote=True`（`"` と `'` を実体参照化）。
- URL は自前で組み立てた ASCII のみの文字列であり、日本語を含まないためエスケープ以上の処理（URLエンコード）は不要。
- テンプレートは f-string でよいが、**エスケープ済みの値のみを差し込む**こと。生の入力文字列を直接埋めない。

## 10. 冪等性

**同じ入力に対して2回走らせたら、`docs/` の全ファイルの内容がバイト単位で同一になること。**

- 生成日時・バージョン文字列・ランダム値・ホスト名などを**出力に一切含めない**。
- 出力は COLUMNS と入力ファイルの内容のみから決定する。
- HTML・PNG とも、**書き込む前に既存ファイルの内容と比較し、同一なら書き込まない**（不要な mtime 更新と git の見かけ上の変更を防ぐ）。
- ディレクトリ作成は `exist_ok=True`。

## 11. `docs/` の更新方式（削除を伴わない）

**既定の方式: 作成と上書きのみ。build.py は一切のファイル・ディレクトリを削除しない。**

- `docs/` および `docs/NN/` が無ければ作る。
- `index.html` と `docs/NN/index.html` は毎回全文を生成して上書きする（内容が同じなら書かない）。
- PNG はコピーで上書きする（内容が同じなら書かない）。

この方式の既知の限界: 過去に出力した画像を COLUMNS から外したり、画像ファイル名を変えたりすると、
`docs/NN/` に古いPNGが残る。残っても index.html から参照されないため表示上の害は無いが、
`docs/` は完全なミラーではなくなる。

`docs/` を毎回まるごと消してから作り直す方式については **§13 の要裁可事項**を参照。

#### キャプションの書き方の指針

キャプションは図が「視覚的にしか示していない関係」を言語化する一文。本文の言い直しではなく、図固有の情報を補う。

- **一文・40字以内・句点は末尾に1つ。**
- 図に並んでいる・積み重ねられている、図中に矢印・枠・色分けがされている、図が左から右へ・上から下へという順序や変化を示しているなら、その関係を明示する。
- 本文に既出の表現は避け、図でしか見えない「比較」「順序」「範囲」「位置」を言語化する。
- 例: 本文が「3種類あります」なら、図が「左から深さ順に3つ並んでいる」ことを「3種類を左から並べ、深さの違いを示しています」と書く。

## 13. 要裁可事項

1. **`docs/` の全消し再生成方式を採るか**
   §11 の既定は「削除しない上書き方式」。完全なミラーにするには実行のたび `docs/` を丸ごと削除して作り直すのが確実だが、
   **削除を伴う操作**であり、`docs/` 直下に人が手で置いたファイル（CNAME、独自の画像など）も消える。
   採用する場合は裁可を仰ぐこと。ディレクターとしての推奨は**既定のまま（削除しない）**。
   古いファイルが気になったときは、そのつど人が確認して消せばよい規模である。

2. **索引に「次回予告」を載せるか**
   最新回の次回予告（例「次回は「え」。」）を索引の末尾に出すと、続きがあることが読者に伝わる。
   一方、公開が遅れると宙に浮いた告知になる。本仕様では**載せない**前提で書いた。載せる場合は指示されたい。

3. **`■ 中継での見つけ方` 節への画像追加方針**
   現状3回とも最終節に画像が無い。今後もこの節は文章のみとするか、回によって図を足すかは編集方針の問題であり、
   build.py 側は COLUMNS に1行足せばどちらにも対応できる。方針の確認のみ。
